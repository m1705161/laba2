# Гайд 3-ДОП. Эволюция схемы в Iceberg (Trino)

Дополнение к гайду 3. Учимся менять схему таблицы Iceberg **без перезаписи данных**: добавлять / переименовывать / удалять колонки, расширять тип, эволюционировать вложенные структуры, читать старые версии таблицы (time travel) и менять партиции.

Всё делается в **DBeaver**, поверх того же стека **MinIO → Lakekeeper → Trino** и каталога **`bench`** из гайда 3. Никакого Spark не нужно — здесь всё на чистом SQL через Trino.

---

## 0. Что это и зачем

В классических форматах (Hive, обычный паркет «вручную») изменить схему — это миграция: переписать все файлы под новый формат. Iceberg делает эволюцию схемы **мгновенной и безопасной** благодаря двум вещам:

1. **Колонки по ID** — каждая колонка хранится с числовым идентификатором, а операции адресуют её по ID, а не по имени/позиции.
2. **Метаданные отдельно от данных** — изменение схемы — это новая версия метаданных, файлы не переписываются.

Итог: `ALTER TABLE ADD COLUMN` на таблице в терабайт выполняется за миллисекунды, потому что физически ничего не двигается.

## 2. Создаём таблицу со всеми типами

Таблица `user_events` — «события пользователя»: в ней встретятся и примитивы, и сложные типы. Выполни в DBeaver:

```sql
DROP TABLE IF EXISTS bench.lakehouse.user_events;

CREATE TABLE bench.lakehouse.user_events (
    event_id     bigint,
    user_id      bigint,
    event_type   varchar,
    retry_count  integer,
    is_active    boolean,
    score        double,
    price        decimal(10, 2),
    created_at   timestamp,
    tags         array(varchar),
    attrs        map(varchar, varchar),
    meta         row(device varchar, os varchar)
) WITH (format = 'PARQUET', partitioning = ARRAY['event_type']);
```

> 💡 `DROP TABLE IF EXISTS` в начале — чтобы гайд можно было прогонять заново с чистого листа. `partitioning = ARRAY['event_type']` — это аналог `PARTITIONED BY (event_type)` из Spark.

Наполним данными. Обрати внимание на синтаксис сложных типов в Trino: массив — `ARRAY[...]`, словарь — `MAP(ARRAY[ключи], ARRAY[значения])`, структура — `CAST(ROW(...) AS ROW(...))` (cast нужен, чтобы Trino знал имена полей):

```sql
INSERT INTO bench.lakehouse.user_events VALUES
(1, 100, 'click', 0, true, 3.5, 9.99, TIMESTAMP '2026-01-01 10:00:00',
 ARRAY['mobile', 'web'],
 MAP(ARRAY['lang'], ARRAY['ru']),
 CAST(ROW('iphone', 'ios') AS ROW(device varchar, os varchar))),
(2, 101, 'view',  1, true, 1.0, 0.00, TIMESTAMP '2026-01-02 10:00:00',
 ARRAY['desktop'],
 MAP(ARRAY['lang'], ARRAY['en']),
 CAST(ROW('pixel', 'android') AS ROW(device varchar, os varchar))),
(3, 102, 'click', 2, false, 5.0, 19.99, TIMESTAMP '2026-01-03 10:00:00',
 ARRAY['mobile'],
 MAP(ARRAY['lang'], ARRAY['ru']),
 CAST(ROW('galaxy', 'android') AS ROW(device varchar, os varchar)));

SELECT * FROM bench.lakehouse.user_events ORDER BY event_id;
```

## 3. Типы данных в Iceberg

| Категория | Типы | Примечание |
|---|---|---|
| Логический | `boolean` | true / false |
| Целые | `integer`, `bigint` | 32 / 64 бита |
| Дробные | `double`, `decimal(P, S)` | `decimal` — точная арифметика денег |
| Строки | `varchar` | `string` из Spark в Trino называется `varchar` |
| Время | `timestamp` | в Trino ещё есть `timestamp(p)` без таймзоны |
| Сложные | `array(...)`, `map(k, v)`, `row(...)` | `struct` из Spark → `row` в Trino |

Наша таблица уже покрывает все категории. Дальше — операции эволюции.

## 4. ADD COLUMN — добавить колонку (безопасно)

Новая колонка появляется **только в метаданных**. В уже записанных файлах её нет, поэтому старые строки читают значение **NULL**. Перезаписи данных нет — операция мгновенная.

```sql
ALTER TABLE bench.lakehouse.user_events ADD COLUMN browser_version varchar;
```

Вставим новую запись, которая уже несёт значение колонки, и посмотрим на разницу:

```sql
INSERT INTO bench.lakehouse.user_events VALUES
(4, 103, 'click', 0, true, 2.5, 4.99, TIMESTAMP '2026-01-04 10:00:00',
 ARRAY['mobile'], MAP(ARRAY['lang'], ARRAY['ru']),
 CAST(ROW('iphone', 'ios') AS ROW(device varchar, os varchar)), '17.4');

SELECT event_id, browser_version FROM bench.lakehouse.user_events ORDER BY event_id;
```

Старые строки (1–3) покажут `NULL`, новая (4) — `17.4`.

---

## 5. RENAME COLUMN — переименовать колонку

Iceberg отслеживает каждую колонку по **уникальному ID**, а не по имени и не по позиции. Поэтому rename — это правка только отображаемого имени в метаданных: старые файлы читаются корректно, потому что ссылаются на тот же ID. Партиционный столбец тоже переименуется — это та же колонка.

```sql
ALTER TABLE bench.lakehouse.user_events RENAME COLUMN event_type TO action_category;

SELECT event_id, action_category FROM bench.lakehouse.user_events ORDER BY event_id;
```

---

## 6. DROP COLUMN — удалить колонку

Колонка исчезает из схемы — читатели её больше не видят. Сами данные **физически остаются** в файлах (вернёмся к этому в разделе про снимки). Drop не «сдвигает» соседние колонки.

```sql
ALTER TABLE bench.lakehouse.user_events DROP COLUMN browser_version;

SELECT * FROM bench.lakehouse.user_events ORDER BY event_id;
-- колонки browser_version больше нет
```

---

## 7. Расширение типа (widen) — integer → bigint

Расширяющее изменение (каждое старое значение представимо в новом типе) безопасно: старые данные на диске **не переписываются**, при чтении значение автоматически «повышается».

Синтаксис в Trino — `ALTER COLUMN ... SET DATA TYPE`:

```sql
ALTER TABLE bench.lakehouse.user_events ALTER COLUMN retry_count SET DATA TYPE bigint;

SHOW COLUMNS FROM bench.lakehouse.user_events;
-- retry_count теперь bigint (был integer)
```

> ⚠️ **Сужение ломает.** Обратное (`bigint` → `integer`, `double` → `integer`) Iceberg не даст сделать без перезаписи данных: значение может не представиться в меньшем типе.

---

## 8. Вложенные типы — поле внутри row/struct

Можно эволюционировать и вложенные структуры: добавлять поля в `row`, элементы в `array`/`map`. Существующие записи получают **NULL** в новом поле.

```sql
ALTER TABLE bench.lakehouse.user_events ADD COLUMN meta.app_version varchar;

SELECT event_id, meta FROM bench.lakehouse.user_events ORDER BY event_id;
-- у старых строк meta.app_version = NULL
```

---

## 9. «Под капотом»: колонки по ID

Почему `rename` и `drop` не ломают старые файлы? В метаданных Iceberg каждая колонка хранится вместе со своим числовым **ID**, и файлы ссылаются на ID, а не на имя или позицию. Поэтому:

- переименование — это смена отображаемого имени у того же ID;
- удаление — пометка ID «невидимым», сами данные в файлах остаются.

Сами метаданные (с ID колонок) лежат в MinIO — в бакете `bench`, папка `user_events-…/metadata/` (это те же `metadata/*.json`, которые ты видел в гайде 1). Через Trino/SQL напрямую ID не показать, но эффект «по ID» ты уже видел выше: после `rename` старые данные читаются под новым именем без перезаписи.

> 📌 **Правило из практики:** не полагайся на позицию колонки. Обращайся к колонкам по имени — именно имя Iceberg маппит на ID.

## 10. Снимки и time travel

Каждое **изменение данных** (INSERT/UPDATE/DELETE/MERGE) создаёт новый **снимок** (snapshot) — ссылку на набор файлов, актуальных в этот момент. Благодаря снимкам таблицу можно читать «на любой момент в прошлом».

> ⚠️ **Важно: изменение схемы снимок НЕ создаёт.** `ADD/DROP/RENAME COLUMN`, `SET DATA TYPE` — это только новая версия метаданных. Снимки создают только операции с данными. (В некоторых гайдах пишут «каждое изменение схемы = снимок» — для Iceberg это неточно.)

Посмотрим все снимки таблицы:

```sql
SELECT snapshot_id, operation, committed_at,
       summary['total-records'] AS total_records
FROM bench.lakehouse."user_events$snapshots"
ORDER BY committed_at;
```

Ты увидишь **три** снимка, и у всех трёх операция `append`:

1. **Пустой** — его создал сам `CREATE TABLE` (Trino делает стартовый пустой снимок, `total-records = 0`).
2. **С 3 строками** — наш первый `INSERT` (`total-records = 3`).
3. **С 4 строками** — второй `INSERT` (строка после `ADD COLUMN`, `total-records = 4`).

Колонка `total-records` (достаём её из map'а `summary`) сразу показывает, где данные, а где пустышка.
Всё, что мы наменяли в схеме (ADD/RENAME/DROP/widen), новых снимков **не** добавило.

**Time travel** — читаем таблицу на момент первого `INSERT`, то есть **до** всех изменений схемы. Там снова исходное имя `event_type` (а не `action_category`) и исходный `integer` у `retry_count`:

```sql
-- подставь snapshot_id второй строки (снимок с total-records = 3, то есть первый INSERT)
SELECT event_id, event_type, retry_count
FROM bench.lakehouse.user_events
FOR VERSION AS OF <snapshot_id>;
```

`FOR VERSION AS OF` читает и данные, и схему на тот момент — поэтому вернулось старое имя колонки. Есть и вариант по времени: `FOR TIMESTAMP AS OF TIMESTAMP '…'`.

> 💡 **Это и есть «откат».** Time travel откатывает **данные** (и схему на тот момент), но это *чтение в прошлое*, а не правка настоящего. Чтобы отменить неудачное изменение схемы в настоящем — примени обратный `ALTER` (например `RENAME COLUMN action_category TO event_type`). А вот откатить изменение *данных* (например случайный `DELETE`) штатно можно только через пересборку на основе старого снимка.

## 11. Эволюция партиций

В классическом Hive смена партиции требовала полной перезаписи таблицы. В Iceberg партицию можно заменить — это тоже операция над метаданными, файлы не трогаются. Старые файлы продолжают читаться рядом с новыми.

В Trino партиция задаётся свойством таблицы `partitioning`. Заменим текстовую партицию `event_type` на `bucket(16, user_id)`:

```sql
ALTER TABLE bench.lakehouse.user_events
SET PROPERTIES partitioning = ARRAY['bucket(user_id, 16)'];
```

Проверь, что данные на месте и их не переписывали:

```sql
SELECT count(*) FROM bench.lakehouse.user_events;   -- те же 4 строки

SELECT * FROM bench.lakehouse."user_events$partitions";
-- видно и старые партиции (по action_category), и новую (bucket по user_id)
```

> ⚠️ Отличие от Spark: в Trino партиция **заменяется целиком** одним свойством (`SET PROPERTIES partitioning`), а не добавляется/удаляется по одному полю (`ADD/DROP PARTITION FIELD`, как в Spark). Суть та же: это метаданные, старые файлы не переписываются, старые и новые партиции читаются вместе.

---

## 12. Шпаргалка: что безопасно, что ломает

От самого безопасного к самому рискованному:

| Операция | Оценка | Почему |
|---|---|---|
| `ADD COLUMN` | ✅ безопасно | NULL для старых данных, файлы не трогаются |
| `ADD COLUMN` в `row` | ✅ безопасно | новое поле структуры = NULL у старых строк |
| `widen` (integer→bigint, double→decimal) | ✅ безопасно | старое значение представимо в новом типе |
| `RENAME COLUMN` | ⚠️ безопасно в БД, рискованно операционно | старые читатели ищут колонку по имени |
| `DROP COLUMN` | ⚠️ осторожно | колонка исчезает; вернуть — только обратным `ADD` (данные в файлах остаются, но новую колонку Iceberg создаст с новым ID) |
| сужение (bigint→integer, смена масштаба decimal) | ❌ ломает | значение может не представиться — нужна перезапись |
| reorder (`FIRST`/`AFTER`) | — | в Trino не поддерживается (есть в Spark; чисто косметика) |

### Правила дисциплины

- Давайте колонкам **осмысленные имена** (не `c1`, а `customer_referral_code`).
- **Новые поля — необязательные** (NULL-допустимые), чтобы не ломать старых читателей.
- **Одно изменение — один коммит** (изолированные, аддитивные правки).
- Относитесь к изменению схемы **как к релизу**, а не к технической правке: тестируйте, коммуницируйте с downstream-потребителями (BI, дашборды, ETL).
- База делает техническую часть простой, но **управление изменениями остаётся на вас**.

## 13. Итог

Iceberg делает эволюцию схемы **мгновенной и безопасной** благодаря двум вещам:

1. **Колонки по ID** — операции адресуют колонку по идентификатору, а не по имени/позиции.
2. **Метаданные отдельно от данных** — изменение схемы — это новая версия метаданных, файлы не переписываются.

Эволюция схемы — это **операция над метаданными**, а не миграция данных.

## 14. Остановить и удалить

Таблица `user_events` живёт в том же томе `minio-data` (бакет `bench`) и базе Lakekeeper (`pg-data`), что и гайды 1–3. Убрать только эту таблицу:

```sql
DROP TABLE bench.lakehouse.user_events;
```

Полная очистка всего стека — как в гайде 1, §7 (контейнеры `docker rm -f`, тома `docker volume rm`, образы `docker rmi`).
